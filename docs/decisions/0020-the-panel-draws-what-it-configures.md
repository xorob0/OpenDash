# ADR 0020: The panel draws what it configures, with SimHub's own renderer

**Date:** 2026-09-22
**Status:** Accepted. Amends [ADR 0003](0003-plugin-settings-through-properties.md), whose "the
plugin does not render" is the line this crosses, on the terms ADR 0003 itself set. Leaves
[ADR 0001](0001-simhub-native-rendering.md) untouched, and does not trigger the fidelity check
[ADR 0008](0008-how-a-pull-request-renders-a-dash.md) attaches to a preview renderer, for the single
reason that nothing here renders. Written for [#398](https://github.com/xorob0/OpenDash/issues/398)
and implemented by [#399](https://github.com/xorob0/OpenDash/issues/399).

## Context

The Rig tab configures a screen on a picture of itself, and the picture is rectangles. `PanelFacePlan`
scales each face's own proportions to the width of the pane, which is the right idea and is where the
value stops: a driver choosing between `Opponents` and `Relative` is choosing between two empty boxes,
and the quick glance cannot be judged without holding a wheel button. Everything the panel writes is an
ordinary SimHub property and everything the face draws is a binding reading one, so a preview does not
have to be told what a setting does. It is the same mechanism the dashboard uses, shown one pane
earlier.

Three refusals appear to stand in front of that, and the interesting part of this record is that two
of them turn out not to apply.

**Our own renderer**, [ADR 0001](0001-simhub-native-rendering.md). OpenDash renders through SimHub
and reversing that would discard everything SimHub does for DDUs, USB screens, phones and the
seventeen sims it reads.

**A preview renderer owes a fidelity check**, [ADR 0008](0008-how-a-pull-request-renders-a-dash.md).
That record priced a TypeScript renderer at thirteen points before it draws a frame and sixteen
before the frame can be believed, and its argument was not the points. It was that a second
implementation of somebody else's expression language diverges silently, as `left([Class], 4)` did
for months. It named "somebody wanting the preview renderer for its own sake" as a new decision
rather than a reversal, and said that decision would still owe the check.

**The plugin does not render, does not read telemetry and does not compute**,
[ADR 0003](0003-plugin-settings-through-properties.md). That line has one stated exception already:
[ADR 0018](0018-the-cars-own-lights.md) reopened it for the car's own lights, so `DataUpdate` exists
and turns three telemetry values into a frame of colours.

## What the assembly turned out to carry

The options were priced against `plugin/lib/SimHub.Plugins.dll`, which is the reference assembly the
plugin already compiles against, at the 9.12.6 the format notes were verified against. Read out of its
metadata:

| Type | What it is |
|---|---|
| `…GraphicalDash.Windows.Renderers.WPFRenderer` | public, public parameterless constructor, `SetCurrentModel(EditorModel, bool)`, `Dispose()` |
| `…GraphicalDash.DashHostRendering` | its base, carrying a settable `ShownScreen` |
| `…GraphicalDash.DashHostBase` | its base in turn, and a plain `System.Windows.Controls.UserControl` |
| `…GraphicalDash.EditorModel` | public, with a public static `LoadFromFile(string fileName, bool edit, string contextId)` |

A `UserControl` can be put in a pane of the settings page like any other control, and a `.djson` under
`DashTemplates` can be loaded by the same call SimHub loads it with. Consequently the preview is not a
rendering of the dashboard. It is the dashboard, drawn by the engine the driver's screen uses, reading
the properties the panel has just written, evaluated by SimHub's own NCalc engine.

## The options

**A. Host SimHub's renderer.** What is described above.

**B. Our own WPF preview.** Walk the `.djson` in the plugin and draw it with WPF primitives. This is
option A of ADR 0008 in a different language, and it acquires the same failure: two renderers, one of
which is wrong in a way nothing reports. It also needs the evaluator, since a scene graph without its
bindings is a still life.

**C. Captured thumbnails.** What [#389](https://github.com/xorob0/OpenDash/issues/389) asked for: one
picture per catalogue page, generated by the dash build and embedded beside the packages. It needs no
renderer and no telemetry, and it draws before anything is installed, which is the one thing A cannot
do. It also cannot show a setting, since a capture is of a page rather than of a configuration, and
several hundred captures inside the plugin is a size somebody downloads.

**D. Open SimHub's own editor.** Send the user to Dash Studio, whose Overview panel already draws every
screen of a package as a live thumbnail. It costs nothing to build and it answers the question in
another window, which is the window the panel exists to save them from.

## Decision

**A. The panel hosts SimHub's own `WPFRenderer`, loads the installed `.djson` with
`EditorModel.LoadFromFile`, and puts it under the screen's name on the Rig tab. Every kind of screen
gets one.** There is no second renderer, no second evaluator, no golden image and no fidelity check,
because there is nothing to keep honest: a difference between the preview and the driver's screen
would be a difference between SimHub and itself.

**ADR 0003's line moves exactly this far and no further.** The plugin still computes nothing and
still reads no telemetry of its own. What it now does is host a control that reads the same property
store the dashboard reads. The distinction is worth keeping sharp, because the cheap next step from
here is to start feeding the preview values of our own, and that is a different record.

**What is ours is four decisions and they are all arrangement**: which file to load, which screen to
show, how large to draw it, and when to stop drawing. The third is in `PanelPreview.cs`, where a test
holds it, and it is uniform: a page is laid out for the shape of the box it is given, so the preview
scales the whole dashboard by one factor and never re-lays anything out. It never enlarges past actual
size, so a 480 round preview is exactly the pixels the driver's screen draws.

**The preview's screen state is filed under an id of its own**, `OpenDashPanelPreview.<namespace>`,
so that a preview cannot write into what the driver's own dashboard opens on.

**#389 is closed as superseded.** Option C's one advantage over this, drawing before anything is
installed, is real and is not delivered here: where a screen's package is missing the pane draws no
preview at all and leaves the warning row that already says so to speak for itself.

## What this costs, stated plainly

**It draws nothing before a package is installed.** A user on the Install tab deciding which face to
install sees no picture of any of them, which is the case option C would have answered and the one
[#85](https://github.com/xorob0/OpenDash/issues/85) will have to answer some other way.

**It is a second consumer of a renderer built for a dash window.** `InitialPlacementDone` exists
because a window tells the renderer when it has been placed, and nothing in the public surface says
what a renderer that is never told does. Every call into SimHub here is wrapped, and a preview that
throws costs one line of text in the pane rather than the settings page.

**Screen selection is the one piece of the window's job done here.** A window decides which screen is
showing; a renderer on its own is handed one. The preview follows the first screen the dashboard
reports as enabled, on a one-second timer, which is slow because what it follows changes when a
setting changes rather than when a frame is drawn. Whether this is needed at all is the first thing
to establish on the VM: if `SetCurrentModel` leaves `ShownScreen` filled, the follower is dead weight
and should go, since the whole value of the approach is that SimHub decides and we do not.

**Nobody has measured what it costs the machine.** A renderer in the panel draws while the driver's
own dashboard draws, on the machine that is also running the car. The preview is let go whenever the
tab is left or rebuilt, which is the cheap half of the answer; the other half is a measurement that
has not been taken.

## Unresolved

**Whether the strips and the matrix follow the same path.** `LedsPreviewEx` and `MatrixPreviewEx` are
public controls of the same kind, which is why [#400](https://github.com/xorob0/OpenDash/issues/400)
and [#401](https://github.com/xorob0/OpenDash/issues/401) were written against this record. They are
not the same case, though, and the difference is the part this record cannot settle for them: a dash
renderer is handed a model and reads the property store itself, whereas an LED preview is handed a
model of colours that something must compose. If SimHub's own composition is not reachable from a
plugin, composing our own profile is a second effect engine, and that is the thing ADR 0008 declined
to acquire. Neither ticket may assume this record covers it.

**Whether the browser demo inherits anything.** It does not inherit the approach:
[#395](https://github.com/xorob0/OpenDash/issues/395) has neither SimHub's renderer nor its
evaluator, so ADR 0019 answers a genuinely different question and the sixteen points ADR 0008 priced
are still in front of it. What crosses over is the rule about the fit and the vocabulary of states,
which is why both live in `PanelPreview.cs` rather than inside the WPF.
